# i18n developer guide

Two independent translation systems live in this app. Mixing them up — using the wrong tool, or
forgetting that one of them needs a manual reactivity nudge — is the most common way to ship a
string that silently never translates.

## The two systems

| | **UI strings** (Lingui) | **Game data text** (CSV)                                                                     |
| --- | --- |----------------------------------------------------------------------------------------------|
| What | Brico's own copy: nav, settings, table chrome, tooltips | Item/building/etc. `name`, `description`, `tag`, … — text baked into the game's data         |
| Source of truth | `src/locales/*/messages.po`, translated via Crowdin | One CSV per locale on the asset CDN, extracted from game assets via BitCraftToolBox/automata |
| Setting | "Interface language" | "Game data language"                                                                         |
| Locale list | `UI_LOCALES` (`src/lib/i18n.ts`) | `DATA_LOCALES` (`src/lib/data-translation.ts`)                                               |
| Matching | Lingui message IDs (hashed from source text) | Exact string equality against a CSV `source` column                                          |
| SSR | English only (client picks the real locale after hydration) | English only, always                                                                         |

They're kept apart because they have different owners (Crowdin vs. an upstream CSV we don't
control) and different reliability (Lingui catalogs are incomplete until translated by volunteers; the CSVs are
of varying AI-generated quality but complete for all locales). Don't try to unify them. The one place they *do*
meet is `~/lib/labels` (below), for the handful of UI labels that are named after the game's own vocabulary.

## Quick reference: which tool, when

| I'm writing... | In a component? | Use                                                                                                                                                                |
| --- | --- |--------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| App-authored UI copy, JSX | Yes | `<Trans>Some text</Trans>`                                                                                                                                         |
| App-authored UI copy, plain string (prop, attribute, non-JSX) | Yes | `useLingui()`'s ``_(msg`Some text`)``                                                                                                                              |
| App-authored UI copy, plain string | No (module scope / plain helper) | `trackUILocale()` once per function, then the bare `t` macro                                                                                                       |
| A label that mirrors game vocabulary ("Items", "Cargo", a sidebar section) | Either | ``gameText(msg`Items`)``, resolved with `useLabel()` / `labelText()`                                                                                                |
| A label that mirrors game vocabulary *and* has an argument ("Tier 3") | Either | ``gameText(msg`Tier ${props.tier}`)`` — the game's own strings use `{0}` placeholders too                                                                            |
| Game-data row fields (`name`, `description`, `tag`, …) | Either | Already handled — see below, no per-call-site work needed                                                                                                          |
| A tag nested inside a row (`rarity.tag`, stat tag, equipment slot) | Either | `game-strings.ts`'s `*Label()` functions                                                                                                                           |
| Sorting user-visible text | Either | `compareText(a, b)`, not bare `localeCompare()`                                                                                                                    |
| Comparing a game value against a hardcoded English literal | Either | `sourceRow(row)` first, then compare — never compare the translated field                                                                                          |
| A count-dependent string ("1 result" / "2 results") | JSX | `<Plural value={n} one="# result" other="# results"/>`                                                                                                             |
| A count-dependent string | Non-JSX | `plural(n, {one: "# result", other: "# results"})` (from `@lingui/core/macro`), wrap the result in `msg({message: ...})` if you need a `Label`/descriptor out of it |

## UI strings (Lingui)

Everything here is `src/lib/i18n.ts` plus the Lingui packages. The single `i18n` instance holds the
app's own catalog; `I18nProvider` (in `app.tsx`) wraps the app so components can read it reactively.

- **`<Trans>...</Trans>`** (`@lingui/solid/macro`) — the default for JSX. Reactive automatically:
  it's a component, subscribed to the active locale through context. Interpolate with `{expr}`
  directly inside it.
- **`` msg`...` ``** (`@lingui/core/macro`) — builds a `MessageDescriptor` (``{id, message}``) without
  rendering anything. Use this when you need to *store* a translatable string for later — a table
  column's `meta.label`, a `Label` value, an option list built once and rendered many times. It does
  nothing on its own; something has to resolve it (`_()`, `i18n._()`, or `useLabel()`/`labelText()`
  if it's wrapped in `gameText()`).
- **`useLingui()`** (`@lingui/solid`) → `{_, i18n}`. Call inside a component; `_(descriptor)`
  resolves a `msg` descriptor to a string, reactively. Use this for plain-string props (`placeholder=`,
  `aria-label=`, a `Select` option's `label`) where `<Trans>` doesn't fit because the consumer wants
  a `string`, not JSX.
- **`` t`...` ``** (`@lingui/core/macro`) — looks like `msg` but resolves *immediately* against the
  module-global `i18n` instance, compiling to `i18n._(...)`. **Not reactive** — see the gotcha below.
  Only use it outside a component (a plain helper function, a module-scope factory), and always
  call `trackUILocale()` first in that function.
- **`i18n._(descriptor)`** — the non-macro escape hatch for module scope. This is what `labelText()`
  uses internally. Same reactivity caveat as `t`.
- **`trackUILocale()`** (`~/lib/i18n`) — reads a signal for its side effect only (`void uiLocale()`).
  Call it as the first line of any non-component function that resolves `t` or `i18n._()`, so the
  *caller's* memo/computation re-runs on a locale change. See `relations.ts` and `placeables.ts` for
  the established pattern — every recipe/name-composing helper there starts with it.
- **`compareText(a, b)`** — locale-aware sort via a cached `Intl.Collator` on the UI locale. Reactive
  the same way `t` is (reading `uiLocale()` internally) — call it inside a computation that's meant
  to re-run on a locale change, e.g. inside the `sort()` callback of a `createMemo`, not once outside
  one.
- **`<Plural>` / `plural()`** — count-dependent strings need pluralization rules (`one`/`other`, or
  more forms for languages like Polish/Russian), not string concatenation with a number. `<Plural>`
  is the JSX form; `plural()` from `@lingui/core/macro` is the value form, usually wrapped in
  `msg({message: plural(...)})` when a `Label`/descriptor is what's needed at the call site.

### ⚠️ Gotcha: `t` and `i18n._()` are not reactive by themselves

`@lingui/core/macro`'s `t` compiles to a read of the module-global `i18n` instance. Nothing
subscribes to it. Inside a component, always prefer `<Trans>` or `useLingui()`'s `_` — both go
through `I18nProvider`'s context and update automatically. Outside a component, `t`/`i18n._()` are
fine, but the *caller* needs a reason to re-run when the locale changes, which is what
`trackUILocale()` provides. Forgetting it doesn't error — it just leaves stale text on screen until
something unrelated happens to invalidate the memo, which is exactly the kind of bug that survives
review.

### ⚠️ Gotcha: `msg` loses its `.message` text in production unless pinned

Lingui's babel plugin defaults to emitting only `id` (a hash) in production builds, dropping the
literal English text from the descriptor. This app pins `descriptorFields: "message"` in
`app.config.ts` so `.message` is always present — `gameText()` depends on it (see below). Don't
"clean up" that config option.

## Game data text (CSV)

Everything here is `src/lib/data-translation.ts`. There's no `t`/`msg`-equivalent macro — it's plain
runtime string matching against a downloaded CSV, keyed by **exact equality on the English source
string**.

- **Row fields are already handled.** `translateRow()` (called from `spacetime.ts`'s
  `BitCraftTable`) rewrites every field listed in `TRANSLATABLE_FIELDS` on every row, reactively, as
  soon as the active data locale's CSV is loaded. If you're reading `item.name` or
  `recipe.description` off a table, it's already translated — there's nothing to call at the
  call site. Only touch `TRANSLATABLE_FIELDS` when adding a genuinely new player-facing string field
  (re-run `npm run i18n:audit-fields` first).
- **`translateGameText(source: string)`** — the standalone form, for English strings not reachable
  through a row: composed text, or the tag → name tables below. Reactive (reads
  `activeDataLocale()`); returns `source` unchanged on `en`, while the CSV is loading, or on any
  miss. This is what `game-strings.ts` and `gameText()` build on.
- **`sourceRow(row)`** — returns the *untranslated* row. Required whenever code compares a
  translated field against a hardcoded English literal (`sourceRow(resource).tag === "World
  Event"`). Comparing the translated field directly breaks under any non-English data locale — grep
  for new `=== "<English literal>"` comparisons against row fields whenever you add one.
- **`game-strings.ts`** — for tags nested inside a row (`ItemDesc.rarity.tag`,
  `CsvStatEntry.id.tag`, `EquipmentDesc.slots[].tag`), which `translateRow` can't reach (and
  shouldn't — those tags are load-bearing identity, not display text). Two-step: tag → official
  English name (a hand-maintained table, e.g. `MaxHealth` → `"Maximum Health"`), then English name →
  translated via `translateGameText`. Use the `*Label()` functions (`statLabel`, `rarityLabel`,
  `equipmentSlotLabel`, …) to display; use the `*Name()` functions (stop after step 1) when you need
  the canonical English value — sorting, URL params, filter keys.

Data locale is a client-only Settings preference. `setActiveDataLocale()` throws if called on the
server — it's module-level mutable state and one Cloudflare isolate can interleave requests from
different visitors, so writing it per-request would leak one visitor's locale into another's
response. SSR is always English; don't try to make it locale-aware by touching this signal.

## Labels — where the two systems meet

`src/lib/labels.ts`. A handful of UI labels are named after concepts the game itself already
translates (most sidebar titles are BitCraft's own compendium section names; "Items", "Cargo",
"Rarity", …). Inventing a second English-to-X translation for those would just give players two
different wordings for the same thing, so they resolve through the game's catalog by default —
but a Crowdin translator can still override the wording for a specific label, and that override
wins.

- **`type Label = MessageDescriptor | GameLabel`** — accepted anywhere a piece of display text is
  needed generically (`ColumnMeta.label`, `DetailProperty.label`, sidebar entry titles, …). A plain
  `` msg`...` `` descriptor is a `Label` too; most call sites don't need `gameText()` at all.
- **`` gameText(msg`Items`) ``** — marks a label as game vocabulary. `source` defaults to the
  descriptor's English text (so the two can't drift); pass a second argument only when the app's
  wording differs from the game's own (``gameText(msg`Weapons`, "Weapon")``, because the game only
  has a singular form - the Crowdin translator can then provide a plural form if needed).
- **Interpolated labels work too.** The game's CSV carries ICU-style placeholders in its own source
  strings (`Tier {0}`, `Requires a Tier {0} {1} equipped to {2}`), and Lingui's `msg` macro leaves
  the same placeholders in the msgid — so `` gameText(msg`Tier ${props.tier}`) `` matches the CSV
  row `Tier {0}` and renders `Palier 3`. Matching is still exact equality on the *unfilled*
  template; the values are substituted back afterwards, by name where the names line up and by
  argument order where they don't. That fallback matters because Lingui only numbers a placeholder
  when the interpolated expression isn't a plain identifier: `` msg`Tier ${props.tier}` `` gives
  `Tier {0}` (matches), `` msg`Tier ${tier}` `` gives `Tier {tier}` (doesn't — pass
  `` gameText(msg`Tier ${tier}`, "Tier {0}") ``). Check the msgid in `src/locales/en/messages.po`
  after `npm run i18n:extract` if you're unsure which one you got.
- **Resolution priority: UI-translator override → game catalog → English.** Concretely: resolve the
  Lingui message first; if a translator has actually overridden it (the resolved text differs from
  the English source), that wins outright. Otherwise, try the game catalogs' translation of the
  source string; if that hits, use it. Otherwise, English. This lets Crowdin correct or replace a
  game-vocabulary label without needing a separate "override" flag — an untouched catalog entry
  resolves to the English source unchanged, which is indistinguishable from "not yet translated" and
  is exactly the case that should fall through to the game's own wording.
- **`useLabel()`** — hook form, call inside a component. Returns a resolver function; reactive on
  *both* locales (UI and data) because it reads both `useLingui()`'s `_` and `translateGameText`
  internally. Don't call it once and cache the string — call the resolver inside the render/JSX that
  needs it.
- **`labelText(label)`** — non-hook form, for module-scope helpers building JSX/strings outside a
  component (`breadcrumb()` in `Nav.tsx` is the reference example). Same reactivity caveat as the
  bare `t` macro: call `trackUILocale()` first if the caller needs to re-run on a UI locale change.
- **`labelSource(label)`** — the canonical **English** text, not reactive, for identity uses (a
  persisted key, a `name`/`id`-style prop) where a `Label` is accepted for display but the value
  must stay stable across locales.

## File map

| File | Owns |
| --- | --- |
| `src/lib/i18n.ts` | `UI_LOCALES`, locale detection/matching, catalog loading (`activateUILocale`), `uiLocale`/`trackUILocale`, `compareText`, Crowdin in-context editor / pseudolocale plumbing |
| `src/locales/*/messages.po` | Lingui catalogs, one per UI locale, edited via Crowdin (English is hand-edited; extracted by `npm run i18n:extract`) |
| `lingui.config.ts` | Lingui's own locale list and extraction config — must mirror `UI_LOCALES` |
| `src/lib/data-translation.ts` | `DATA_LOCALES`, `activeDataLocale`/`setActiveDataLocale`, CSV fetch/parse, `translateRow`, `translateGameText`, `sourceRow`, `TRANSLATABLE_FIELDS` |
| `src/lib/game-strings.ts` | Tag → official-name tables and `*Label()`/`*Name()` for rarity, stats, equipment slots, etc. |
| `src/lib/labels.ts` | `Label`, `gameText()`, `useLabel()`, `labelText()`, `labelSource()` — the UI/game-text bridge |
| `src/lib/spacetime.ts` | `BitCraftTable`'s reactive translation of row data on the client (wires `translateRow` in) |
| `src/app.tsx` | `AppRoot` syncing persisted Settings → `activateUILocale()` / `setActiveDataLocale()` |
| `src/routes/settings.tsx` | The two locale pickers ("Interface language", "Game data language") |
| `scripts/i18n/*` | `extract` (catalog generation), `audit-fields` (which row fields are translatable), `verify` (smoke-test the data layer against a real CSV) |

## Caveats to avoid

1. **Never build a shared lookup with a lazily-created `createMemo`.** Solid disposes a memo when
   its owning component unmounts, leaving the last value readable but frozen — a module-scope cache
   built inside the first caller's component silently stops updating the moment that component
   unmounts. Use `derivedTableLookup`/`derivedFromRows` (`spacetime.ts`) for module-scope lookups
   instead. This has bitten this codebase twice; read the doc comment on `derivedFromRows` before
   writing a new one.
2. **`t` / `i18n._()` need `trackUILocale()` outside a component.** See the Lingui section above.
3. **Compare game data with `sourceRow(row)`, never the translated field.** A hardcoded English
   literal will stop matching the moment the data locale changes.
4. **`TRANSLATABLE_FIELDS` is an allow-list.** Adding a table with a new string field doesn't
   automatically translate it — and that's intentional (asset paths, animation IDs, and style values
   look like strings too, and translating them corrupts sprites, not text). Re-run
   `npm run i18n:audit-fields` after a game data update and add genuinely player-facing fields by
   hand.
5. **Game-text column *values* stay English; only the *display* is translated.** Filter state,
   query params, and persisted hidden-column settings must stay locale-independent. `tagColumn` /
   `rarityColumn` / faceted filters already follow this — match it in any new filterable column.
6. **`setActiveDataLocale()` / server-side locale.** Both UI and data locale are client-only,
   module-level mutable state; SSR is always English by design (Cloudflare can interleave requests
   from different visitors in one warm isolate). Don't try to make either locale-aware per-request
   without a genuinely per-request mechanism.
7. **`msg` needs `descriptorFields: "message"` pinned in `app.config.ts`.** Without it, production
   builds drop the English text from every descriptor, and `gameText()`'s default `source` (which
   reads `fallback.message`) silently breaks — every `` gameText(msg`...`) `` call without an explicit
   `source` argument stops matching the game CSV in production only. Already fixed; don't revert it.

## Verification

```bash
npm run typecheck
npm run i18n:extract-check      # UI catalog fresh?
npm run i18n:verify             # data layer vs. a real CSV (pass a locale to change it)
npm run i18n:audit-fields       # re-review TRANSLATABLE_FIELDS after a game data update
npm run build                   # check the EXIT CODE
```
